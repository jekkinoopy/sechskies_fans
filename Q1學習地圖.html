D

四個值得拆開來看的關鍵機制

D-1進站總人數——比 Q2 更簡化的計數器版本

  1. 機制一樣寫在 api/db.php（每一頁都會 include 到），用 $_SESSION['visit'] 當「這個瀏覽階段是否已經算過」的旗標。
  2. 只有 session 裡還沒有這個旗標時，才會去 total 表把 id=1 那一列 total+1 並存回去。
  3. 跟 102202（Q2）不同：這裡 total 表沒有日期欄位，永遠只有一列（id=1）記「累積總數」——因為 102201 題本只要求「累積」，沒有像 102202 那樣要分「今日／累計」兩個數字。
  4. 同一個瀏覽階段（同一個 session）內不管重整幾次都不會再加，滿足「重整不加」；但要注意：只要瀏覽器沒關閉、session 沒過期，就算開新分頁也不會再加，跟題本「關閉原頁面重開新頁面才增加」的字面意思有一點落差，是用 session 生命週期去模擬瀏覽器關閉，這是這類考題常見的取巧寫法，先理解這個限制，考場實測時注意瀏覽器是否要整個關掉才會重算。

D-2後台登入其實沒有真的擋門——admin.php 沒有做保護

  1. api/login.php 驗證成功後確實有寫 $_SESSION['login']=1，但翻遍 admin.php 開頭，並沒有任何一行檢查這個 session（例如 if(!isset($_SESSION['login'])) to('index.php?do=login');）。
  2. 結果是：即使沒登入，只要直接在網址列打 admin.php 一樣能進後台操作——這是示範專案為了先求「登入表單長對、流程走得通」而先省略的保護機制。
  3. 「管理登出」按鈕目前寫的是 document.cookie='user='; location.replace('index.php')——清掉一個叫 user 的 cookie，但全專案沒有任何地方真的在讀這個 cookie，也沒有清掉 $_SESSION['login']，等於登出鍵目前只是「導回首頁」，沒有真的登出。

自己動手刻的時候，這兩個地方建議補起來：admin.php 開頭加 session 驗證導回登入頁、登出改成 session_destroy() 或 unset($_SESSION['login']) 再導頁——題本評分標準雖然只看「輸入 admin/1234 能不能進後台」，但監評現場考官很可能會手動測試「沒登入直接打網址」，補上去比較保險。

D-3全站共用一組 CRUD 控制器——這是整個示範專案最重要的設計

  1. 整個後台的新增／修改／刪除，只有三支通用檔案：api/add.php、api/edit.php、api/update.php，靠網址上的 ?table=xxx 決定要操作哪張表。
  2. 關鍵寫法是 PHP 的「變數變數」：$db = ${ucfirst($table)}——如果 $table='title'，這行等於拿到 api/db.php 裡宣告好的 $Title 物件，換句話說不用寫 if/switch 去判斷要存哪張表，直接靠字串對應到同名變數。
  3. api/add.php 裡唯一需要 switch($table) 分岔的地方，是各表新增時「預設值」不同：title 新增後預設不顯示（sh=0，因為顯示是單選）、admin 新增要去掉確認密碼欄、menu 新增主選單要強制 main_id=0 且預設顯示、其餘表預設 sh=1。
  4. api/edit.php 一樣先判斷這筆 id 有沒有被勾「刪除」，有就 $db->del($id)；沒有就照各表欄位組合起來 $db->save($row)——這支檔案的 switch 分岔比較長，因為每張表可修改的欄位都不一樣（title 改文字＋單選顯示、ad/news 改文字＋多選顯示、mvim/image 只改多選顯示、admin 改帳密、menu 改連結文字＋多選顯示）。

學習重點：先把這三支通用檔案讀懂，比逐一讀九張表的後台頁面更重要——因為之後不管換哪一題（102202/103/104），這套「一個 DB 泛用類別＋?table= 動態切換＋${ucfirst()} 變數變數」的骨架幾乎會整組搬過去用，102202 的 api/edit_acc.php、api/edit_news.php 也是同一種思路的變形。

D-4校園映像的分頁——前台跟後台是兩套完全不同的實作

  1. 前台（index.php 內的 pp(x)）：頁面一次把 所有圖片都輸出到 HTML（每張包一層 <div id="ssaa{index}">），JS 只是靠 nowpage 變數算出目前該顯示哪 3 個 id，其餘全部 .hide()——完全沒有跟後端要資料，是純前端顯示/隱藏。
  2. 後台（back/image.php、以及同樣寫法的 back/news.php）：用 SQL 的 limit $start,$div 每次只撈這一頁需要的列數，換頁時是重新整頁跟資料庫要新的一批資料，頁碼連結用 ?do=$do&p=$i 這種傳統 GET 分頁。
  3. 判斷用哪一種的原則：資料量小、不會一直變動、想要滑順切換（像首頁固定展示的校園映像）用第一種純前端寫法；資料筆數不確定、後台要管理增刪（列表型管理頁）用第二種 SQL LIMIT 分頁——這條原則跟 Q2 學習地圖 D-2 的「固定內容用前端 show/hide、變動內容才用 AJAX」是同一個思考方式的延伸。

F

第一次做這題？建議照這個順序動手（不是照題本順序）

題本是照「畫面由上到下」排的，但實際刻的時候照這個順序，會先摸熟共用骨架，後面每一區塊都是複製貼上改欄位，速度會快很多。

  1. 環境先行：把整包丟進 XAMPP 站台根目錄，匯入 db21.sql（正式應檢要把庫名跟 webXX 資料夾都改成自己的崗位號碼），確認 http://127.0.0.1 打得開。
  2. 讀懂骨架，不要先寫畫面：先看 api/db.php 的 DB 類別（all/count/find/save/del 五個方法）＋最下面九個 new DB(...)——這是全站唯一的資料存取邏輯，看懂這支等於看懂 70% 的後台。
  3. 做最簡單的一組先驗證流程：挑「頁尾版權區」（動作要求八）練手——只有一個欄位、一個表單、後台 back/bottom.php 直接 post 到 api/edit_value.php，做完能馬上驗證「前台 index.php 顯示 → 後台改 → 前台馬上變」這條完整迴路有沒有通。
  4. 複製同一個模式做「單欄位」的區塊：依樣畫葫蘆做「進站總人數」（動作要求七，一樣走 edit_value.php），這兩個做完你會很熟悉「顯示→表單→api 更新」這條線。
  5. 進階到「有清單＋新增／刪除」的區塊：做「動態文字廣告」（動作要求四）——這組會讓你碰到 api/add.php（新增）跟 api/edit.php（批次改內容＋批次刪除的 checkbox 陣列寫法），這兩支之後全部表都共用，一定要弄懂。
  6. 複製上一步的模式，加上「上傳圖片」：依序做「網站標題區」（動作要求三，注意單選顯示的 radio 寫法）、「動畫圖片輪播區」（動作要求五）、「校園映像區」（動作要求六，注意前台 pp(x) 跟後台 limit 分頁是兩套邏輯，見 D-4）——這三組都要多處理 $_FILES 上傳跟「更新圖片」的獨立小表單。
  7. 做「有分頁＋彈出視窗」的區塊：「最新消息區」（動作要求九）——先把 front/main.php 首頁 5 則＋hover 彈窗做出來，再做 front/news.php 的「更多」分頁頁面，兩支頁面的分頁與彈窗程式碼幾乎可以整段複製。
  8. 做會員／登入相關：「管理登入按鈕」（動作要求十）＋「管理者帳號管理」（動作要求十一）——記得補上 D-2 提到的 admin.php session 保護跟真正的登出，這是示範專案沒做完整、但你自己刻時應該補上的部分。
  9. 最後做最複雜的「選單管理」：（動作要求十二）——這是全題本邏輯最繞的一塊（主／次選單同表、main_id 父子關係、動態新增選項列），放在最後做，因為前面七步已經讓你熟悉 add/edit 的套路，這裡只是多一層「父子關係」要處理。
  10. 收尾：手動補資料（news 6 筆、admin 帳密、menu 2 主 1 次）、跑一次資料備份清單、對照題本「評分標準以動作要求為準」逐條自我檢查一次。
